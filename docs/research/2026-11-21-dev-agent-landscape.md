# 主流开发 Agent：能力基线、竞争边界与 Nova 差异化

**日期**：2026-11-21  
**研究问题**：Nova 的开发模式应对齐哪些主流能力，哪些方向值得做独特创新？  
**样本**：Claude Code、Cursor、OpenAI Codex、GitHub Copilot coding agent、OpenHands。它们分别代表终端 Agent、AI IDE、云端任务、GitHub 原生交付、开源/自托管路线，不声称覆盖整个市场。  
**方法**：产品能力以官方文档、官方仓库/文档源码为准；Nova 以本仓库代码与文档为准。未对五款产品做同题实测，**功能存在不等于效果等同**；没有采用市场份额、成功率或性能数字。  
**阅读提示**：【事实】指来源直接陈述或本次直接读到的代码；【推断】是基于这些事实的产品判断；【假设】是尚需用户验证的命题。“未见公开证明”仅指本轮资料范围，不等于功能不存在。

## 0. 结论先行

1. **【事实】“对话→检索/编辑→真实命令或测试→人工审查→Git/PR”已是主流主链路。** 五款产品都有代理式编码与终端/命令执行入口，也都公开支持项目规则/记忆或扩展；但后台恢复、跨端续做与审计深度并不相同。Nova 应把这些主链路能力视为基础体验，而非新卖点。[S1][S7][S11][S15][S18]

2. **【推断】Nova 的近期对齐重点应是 IDE 内反馈、GitHub PR/评审闭环、隔离环境与断点续做，而不是更多模型或又一套聊天 UI。** Nova 已有 Web/桌面/CLI、规则、MCP、权限、后台回合，但 Git 目前以本地初始化、提交、diff、回滚为主；本地模式没有容器隔离；项目间共享也未提供。[N1][N4][N5]

3. **【事实】可观测与审计本身不再是空白。** GitHub 的会话日志展示工具与验证过程，提交链接回日志，并保留作者/共同作者归属；Cursor 提供团队审计 API；Claude Code、Codex、Copilot 均有权限、云端隔离或人工评审机制。[S9][S10][S13][S16][S17]

4. **【推断】Nova 可守住的差异是“证据如何组成一个可复核的交付”，而不是“有一段日志”。** 具体是：结论→代码位置→diff→真实验证→运行环境→审批/提交→文档断言的关联，以及失败和未验证项的明确保留。GitHub 已在“提交→会话”方向很强，Nova 不应声称独家拥有轨迹或归因。

5. **【推断】最值得验证的三个产品方向：**
   - **跨仓库影响与变更包**：以用户授权的多个仓库为一个工程边界，给出依赖证据、需同步修改的仓库与各自验证；
   - **本地/服务器可比性**：不假装无隔离主机与容器相同，而是记录环境差异、采用统一验证清单，并给出可比性结论；
   - **代码→技术文档/作品集证据链**：让文档中每项能力、性能或结果声明能回到代码、测试和运行产物，失效时可重验。

6. **【事实】这些方向并非全是从零开始。** Nova 已有跨多个授权仓库检索、单仓库影响分析、引用存在性检查、红绿任务、轨迹和黄金样例；跨仓库影响、环境等价保证、代码/结果到文档的自动映射尚未形成。[N1][N2][N6][N7][N8]

## 1. 研究口径：怎样定义“标配”

本文将样本内**至少四款有明确官方支持**的能力称为“样本基线”，不是全行业统计。对 planning、subagent、移动入口等差异较大的能力单列“部分普及”。所有单元格只表示有公开的一手支持，不代表默认开启、所有套餐可用或实际质量相同。

- **真实验证**：能实际运行终端命令、构建、测试或 lint，不是模型只写“测试通过”。
- **后台与恢复**：任务离开当前页面后继续，以及恢复会话/工作区；两者不混为一谈。
- **记忆与规则**：区分项目指令文件（确定性注入）与产品记忆的自动学习；不能因有规则文件就宣称有长期记忆。
- **审计**：区分可回放的事件记录、团队管理审计、不可篡改的合规存证。本研究没有证据证明任何样本提供最后一项。
- **可复现**：区分“能看到执行记录”与“在锁定环境中重跑并得到可比较结果”。前者不等于后者。

## 3. 产品证据与竞争边界

### 3.1 Claude Code：终端为主，扩展到桌面、Web 与团队工作流

- 【事实】Agentic coding 工具能读代码、编辑文件、运行命令，并连接 MCP；规划模式与项目 `CLAUDE.md` 提供任务和项目上下文。[S1][S2]
- 【事实】官方文档提供子代理/并行 agent、worktree 隔离与后台会话、会话恢复和 GitHub Actions 等入口；Web/桌面与远程控制可用于查看和延续云端工作。[S3][S4][S5]
- 【事实】权限不是简单的“全部自动”：有只读/询问等模式，企业可管理允许项；Web 云端任务与环境隔离、凭据和网络访问相关约束需单独配置。[S4][S6]
- 【推断】“终端 Agent + 规则 + MCP + 子代理 + PR”是对齐项。对 Nova 而言，差异不应是把终端搬进网页，而是让权限决策和验证结果成为可检查交付的一部分。

### 3.2 Cursor：IDE 内连续编码与云端 Automations 汇合

- 【事实】Cursor Agent 能探索代码库、编辑并运行终端命令；Plan Mode 会研究代码、提出澄清问题并给出可编辑的分步计划；另有规则、diff 审阅与 MCP。[S7][S8]
- 【事实】官方索引文章说明其代码库索引使用 Merkle tree 跟踪变更；检索可同时利用精确文本搜索与语义搜索。[S8]
- 【事实】Cloud Agents 可在隔离远程环境运行任务；Automations 按计划或 GitHub、GitLab、Slack、Linear、webhook 等事件触发，结果可进入 PR/评审工作流。团队另有审计日志 API。[S9][S10]
- 【推断】Cursor 已经把“定时/事件驱动的后台编码”产品化；Nova 不应仅复制定时任务。更可取的是让一次触发生成“变更及其证据”，并把未验证影响明确交给用户。

### 3.3 OpenAI Codex：云端环境与多面任务入口

- 【事实】Codex 提供 CLI、IDE 扩展与云端任务；云环境用于安装依赖、运行代码和测试；任务结果以 diff、命令/检查结果供审查。[S11][S12]
- 【事实】定制层包括 `AGENTS.md`、记忆、技能、MCP 与子代理；官方最佳实践还描述把稳定流程做成 scheduled tasks/automations，并覆盖 CLI、IDE 与 ChatGPT 桌面应用。[S13]
- 【事实】CLI/IDE 有审批与沙箱模式，云端有隔离容器、网络控制；PR 审查和 GitHub/GitLab 集成使其进入代码评审流程。[S13][S14]
- 【推断】“可复用云环境”是主流基线，但不是“每次执行可复现”的证明。Nova 可以将环境描述、依赖锁、镜像/工具版本、输出摘要纳入交付，而非仅保存环境名称。

### 3.4 GitHub Copilot coding agent：PR 是工作单元，审计已进入提交链

- 【事实】任务从 Issue、聊天、VS Code 或 agents panel 发起；Agent 在 GitHub Actions 驱动的临时开发环境中探索、修改、运行测试和 linter，创建/修改 PR 并请求人工评审。[S15][S16]
- 【事实】官方明确限制：一次任务只修改指定仓库，不能跨多个仓库修改；默认上下文也是该仓库，MCP 可扩展上下文；每个任务一个 PR。[S16]
- 【事实】会话日志包含内部推理和用于理解仓库、修改、验证的工具；提交作者为 Copilot、发起人为共同作者，提交信息含会话日志链接，提交有签名/Verified 标记。[S17]
- 【事实】其安全机制包括防火墙、受限分支、工作流运行需有写权限者批准、不能批准或合并自己的 PR；在有审批要求的仓库，发起人不能批准该 PR。安全验证涵盖 CodeQL、依赖 advisory 与 secret scanning，细节可在会话日志查看。[S16]
- 【事实】云会话能在 GitHub Mobile、网页、桌面、CLI 间继续，并保留会话、文件和进行中工作；支持中途 steer、停止与归档。[S17]
- 【推断】这是对 Nova“证据与审计”定位的最强约束：提交到轨迹的追溯、责任归属和独立审批已经是主流能力。Nova 应学习其 PR 与独立评审闭环，同时在 GitHub 之外的本地、自托管、多仓库和文档证据上求差异。

### 3.5 OpenHands：开源、自托管与可嵌入 Agent SDK

- 【事实】OpenHands 提供 Software Agent SDK、Agent Server、本地/云/企业形态和沙箱；开源代码可用于检查实际实现。[S18][S19]
- 【事实】V1 支持 Docker、Process、Remote 沙箱，官方推荐 Docker；旧 V0 Local Runtime 直接在本机执行且明确没有沙箱隔离。[S19][S20]
- 【事实】提供确认/安全策略、MCP、项目指令/微代理和可编程工具接口；适合自托管或嵌入其他工作流。[S18][S21]
- 【推断】“开源+自托管+本地执行”本身并不独特；真正困难的是默认安全配置、环境迁移和证据格式能否跨部署保留。Nova 不应把无隔离的 HostExecutor 与 Docker 沙箱统称为一种安全等级。

## 5. 被低估、适合 Nova 的差异化

### 5.1 从“有日志”升级为“有主张的证据包”

**已有事实**：GitHub 已能把提交追溯至会话；Nova 已记录检索、模型轮次、工具、审批，并能生成命令/退出码、改动、引用、未验证项报告。[S17][N1][N2]

**建议【推断】**：以“主张（claim）”而非工具调用为组织单位：

```text
主张：本次修复消除空列表导致的异常
  ├─ 代码证据：commit / file:line / diff
  ├─ 反例：新增测试在原版本运行失败（红）
  ├─ 修复后：同一测试及回归集合通过（绿）
  ├─ 环境：镜像/依赖锁/工具版本/网络/隔离等级
  ├─ 人工决策：谁批准了什么，之后是否又有修改
  └─ 未证明：未覆盖的平台、数据与性能边界
```

差异化不在收集更多文本，而在：固定输入与基线、把输出与具体 commit 绑定、验证前后代码身份一致、保留反例和人工决定。**不应宣称防篡改或自动证明正确性**：当前 Nova 轨迹是事件记录，不是密码学存证；引用校验也不证明语义。[N2][N3]

### 5.2 跨仓库影响分析：把多仓库检索推进到变更工程

- 【事实】Copilot 明确不能在一次任务跨多个仓库修改。[S16]
- 【事实】Nova 的会话可关联多个授权仓库，`search_code` 与关键词检索支持 `repo_ids` 列表；但 `impact_analysis` 默认取第一个仓库，依赖图 SQL 也都限定单个 `repo_id`。[N6][N7]
- 【推断】这是可落地而非虚构的下一步：先分析，不直接跨仓库写入。

**最小产品**：用户明确选择仓库集合与各自基线 commit → 建立服务/契约/包依赖边 → 列出受影响仓库、接口、测试和证据 → 为每仓库生成独立变更提案与验证任务 → 汇总未验证依赖。

**边界【推断】**：导入图和文本引用不是完整调用图；动态调用、运行时配置、数据库和部署依赖会漏。必须显示“已知/未知”和证据来源，不能只给风险分数。

### 5.3 本地与服务器“一致性”应定义为可比，而不是相同

- 【事实】Nova 服务器使用锁定 Docker 容器；本地主机直接运行、无容器隔离，且本地不使用 Qdrant/embedding，检索路径不同。[N4][N8]
- 【事实】OpenHands 同样区分 Docker 与直接进程执行；Codex 等也分别配置本地/云环境。[S13][S19][S20]
- 【推断】本地优先的战略价值是隐私、低服务器成本与真实项目环境；代价是环境和安全边界不一致。**“一致性”不应承诺相同输出或相同安全性。**

建议定义一张机器可读的 `verification manifest`（概念设计，尚未实现）：

| 字段组 | 用途 |
|---|---|
| 仓库 URL/path 的脱敏标识、commit、工作区 diff 摘要 | 确认测的是哪份代码 |
| 执行模式、OS/arch、隔离等级、网络策略 | 防止把主机通过与容器通过混称 |
| 镜像 digest、运行时与工具版本、锁文件摘要 | 判断环境是否相同/可比 |
| 规范化命令、工作目录、退出码、日志位置 | 支持独立重跑 |
| 测试选择、收集数/通过/失败/跳过、未运行原因 | 不把部分测试写成全部通过 |
| 检索后端与索引版本（问答任务） | 说明本地/云端上下文可能不同 |

优先做**同一验证清单、同一结果 schema、环境差异显式化**，再研究可移植容器。不要把本地敏感环境变量或路径随报告导出。

### 5.4 从代码到技术文档/作品集：让陈述可回到证据

- 【事实】GitHub/Copilot 等已能写文档、生成 PR 描述和总结变更，但本轮资料未见“文档每项断言自动绑定并重验代码/测试/产物”的承诺。[S15][S16][S17]
- 【事实】Nova 已有论文项目关联代码、AI 写作和 `文件:行号` 依据；路线图中环境锁定、沙箱复现、图表/表格→代码/数据证据附录仍是 M3/v0.3+ 规划，不能写成现有功能。[N9][N10]
- 【推断】这比自动生成 README 更有辨识度：交付物不只是“项目介绍”，而是可追溯、可复验的技术证据集。

**建议流程【推断】**：

1. 从用户确认的项目目标生成文档提纲，不让模型自行虚构成果；
2. 每项陈述标注 `代码事实 / 实测结果 / 人工说明 / 未验证`；
3. 代码事实绑定 commit + 文件行号；实测结果绑定验证运行与原始产物；界面结论绑定指定版本截图；
4. 文档生成后自动检查引用目标是否存在、行号是否漂移、数字是否能在结构化结果中找到；
5. commit 变化后标“待复核”，只重验受影响断言；用户确认后才导出作品集/技术说明。

**明确不做【推断】**：不把“有测试”推导为“生产可靠”，不编造性能/用户/业务指标，不用 AI 生成内容替代真实贡献说明。作品集应披露 AI 与人的分工。

### 5.5 可复现任务包：比轨迹回放多一步

【事实】Nova 有黄金仓库回归，覆盖 Python、Node、全栈契约，但需要 PostgreSQL、Docker 与指定镜像；轨迹不支持从任意历史步骤重放。[N5][N11]

【推断】可把这一基础产品化为**可移植任务包**：固定基线、脱敏输入、任务目标、权限白名单、依赖/镜像、验证脚本、允许变动范围、预期断言、原始输出。重点是让第三方在受控环境独立运行，不是回放一条模型输出。

建议分两层：
- **确定性层**：环境准备、测试、静态检查、契约检查、证据收集；必须可无模型重跑。
- **模型层**：记录模型/参数/提示与工具版本，用于解释差异；不承诺相同文本或动作序列。

## 6. 推荐路线图：把结论变成可验收能力

### 6.1 主线与顺序【推断】

**“本地优先的可验证工程交付”**：不另起通用聊天产品或重造 IDE；先统一“验证事实”，再补主流交付闭环，最后把独特方向逐层接到同一证据对象上。以下顺序只表达依赖关系，**不是工期承诺**。

| 顺序 | 阶段目标 | 依赖 | 包含能力 | 通过本阶段后才进入 |
|---|---|---|---|---|
| 0 | **统一验证事实层** | 无 | CAP-01 结果模型；CAP-02 隔离披露 | 证据、PR、跨仓库、文档都以它为事实源 |
| 1 | **主流交付闭环** | CAP-01、CAP-02 | CAP-03 PR/CI/评审闭环 | 可把验证结果作为 PR 的机器可见证据 |
| 2 | **可复核交付** | CAP-01、CAP-02 | CAP-04 证据包/任务包；CAP-07 本地-服务器可比 | 有稳定 schema 后才能扩展证据来源 |
| 3 | **跨仓库影响** | A 类单仓影响能力、CAP-04 | CAP-05 多仓基线与影响报告 | 先只读报告与分仓提案；跨仓写入另立审批能力 |
| 4 | **代码→文档/作品集** | CAP-04、CAP-05（可选） | CAP-06 断言证据链与漂移检测 | 只导出可追溯陈述，不自动生成成果背书 |

P1 的 IDE 内诊断/diff、多客户端续做可以并行做体验调研，但不应早于 CAP-01 改变产品事实模型；否则会再次形成无法统一的结果格式。

### 6.2 可验收能力定义

**CAP-01 统一验证结果（基线）**  
覆盖每条验证的 `passed / failed / not_run / skipped / unsupported`；绑定本次运行的 commit 或工作区 diff 摘要、规范命令、退出码、测试收集/通过/失败/跳过数、开始/结束时间和日志定位。禁止仅凭模型自述或“无输出”判定通过；部分测试通过不得显示为“全部通过”。  
**验收**：人为制造失败、跳过、未运行、工具缺失四类样例，报告与实际命令结果逐项一致；同一 commit 重跑结果可对比。

**CAP-02 隔离事实披露（基线）**  
每条验证和每次命令都显示执行模式（容器/本机）、隔离等级、网络策略、工作目录范围与敏感环境剥离情况；无隔离时不得展示为隔离执行，审批也不能替代沙箱。  
**验收**：同一任务分别在 Docker 与本地模式运行，结果页必须显示不同环境与安全边界；本机执行结果不能通过任何“安全/隔离”筛选。

**CAP-03 PR/CI 与独立评审闭环（基线）**  
在用户明确授权后创建 draft PR，展示 CI 状态与评审意见，允许按评论继续修复；合并、推送主分支和其他外部副作用仍由用户最终决定。GitHub 的独立审批和不能自批说明应作为产品基线参考 [S16][S17]。  
**验收**：使用测试仓库走完“Issue → 改动 → 验证 → draft PR → CI → 评审意见 → 修订”；未授权时无远端写入；自动合并不存在或默认关闭。

**CAP-04 可复核证据包/任务包（差异）**  
把“主张”组织为：结论、代码基线、diff、验证前后状态、环境 manifest、人工决策、未证明事项。确定性层（环境准备、测试、静态/契约检查、证据收集）必须不依赖模型即可在指定环境重跑；模型与提示版本只用于解释差异。  
**验收**：第三方按包独立重跑，不读会话也能判断通过/失败；删除或篡改产物会被校验发现；失败和未覆盖项不会被汇总页隐藏；模型不同不改变确定性层结论。

**CAP-05 跨仓库影响报告（差异）**  
用户选择多个仓库及各自基线 commit，系统基于服务/契约/包依赖和符号引用给出受影响仓库、接口、测试和未知项；为每个仓库输出独立验证任务和变更提案，不把多仓库改动合成一个不透明补丁。静态分析的局限必须随结果展示 [N7]。  
**验收**：至少两个样例仓库的契约变更能列出双向影响；故意加入动态导入/运行时依赖时必须标“未覆盖”；无授权仓库绝不进入检索或报告；跨仓库写入被禁止或走单独授权。

**CAP-06 文档/作品集断言证据链（差异）**  
技术说明或作品集中的每项陈述标注 `代码事实 / 实测结果 / 人工说明 / 未验证`，分别绑定 commit+行号、验证运行与原始产物、作者说明或空证据；commit 或代码变化后自动标记失效并只重验受影响断言。  
**验收**：引用行号漂移、证据产物丢失、数字无法在结构化结果找到时，导出被阻止或显著标错；删除被引用的实现后文档不能继续显示“已核实”；AI 生成说明必须与人的贡献说明区分。

**CAP-07 本地/服务器可比性（差异）**  
同一验证清单在两种模式运行后，输出环境差异表（OS/arch、隔离、网络、镜像 digest、运行时/工具版本、检索后端），并明确“哪些结论可比、哪些不可比”。不承诺相同回答、相同安全等级或相同耗时。  
**验收**：同一仓库分别在本地和容器运行，结果可并排比较且差异齐全；本地检索缺 embedding 时，不能将回答差异归因于代码；敏感路径和环境变量不进入导出。

### 6.3 证据验收而非宣传验收【推断】

- 人为制造一个失败测试，报告必须保留“红→绿”两次真实运行及各自代码身份；
- 删除一行被引用的代码，文档应标失效，不得仍显示“已核实”；
- 本地主机与容器运行同一清单，结果可比较但隔离/环境差异必须展示；
- 跨仓库样例故意引入动态依赖，报告必须暴露未覆盖面，而非宣称完整；
- 模拟进程中断，恢复时不得自动重放未获新授权的外部副作用。

### 6.4 暂不进入路线图

自动合并、自动发布、无人值守跨仓库写入、承诺模型输出完全一致、把自动检查称为学校/企业合规认证、生成无证据的性能或用户数字。它们会削弱证据链，而不是增加差异化。

### 仍待验证的假设

1. 【假设】学生会为“能复核的项目证据/作品集”而非又一份自动 README 付出时间或费用；
2. 【假设】跨仓库影响对个人/小团队足够高频，值得维护多仓库索引与权限；
3. 【假设】用户愿意提供锁文件、容器或环境信息以换可复现性；
4. 【假设】证据包在 GitHub 的会话日志与 PR 审查之外仍有感知价值。应通过真实项目试用，而非功能清单验证。

## 9. 与论文/文档方向的连接

【推断】开发模式的差异不应单独停在“更好写代码”。论文项目关联已经提供入口；下一步是共用同一证据对象，把代码、测试、实验产物、文档陈述连起来。这与另一项论文/文档调研的交集是**证据与复现**，不是新增一个互相隔离的写作 Agent。任何论文模式集成都必须遵守“不代写、不伪造引用、不将自动检查称为学校合规认证”的现有边界。[N9][N10]

**一句话结论**：主流 Agent 已经会读、改、跑、审、交付，也开始会留日志；Nova 不应复制这条功能清单，而应把“交付为什么可信、在哪能重跑、哪些仍不知道”做成跨仓库、跨环境、跨代码与文档的可检查证据链。
