# Nova Agent 文案规范

> 日期：2026-11-21  
> 状态：M1 基线，随产品能力更新  
> 适用范围：宣传页、`/guide`、下载/登录页、产品内对话与提示词、审批卡、错误/空状态、通知、导出报告。  
> 关联：[产品升级路线图](PRODUCT-UPGRADE-ROADMAP.md) §5.4

---

## 1. 语气

1. **具体**：说清楚“做什么、会发生什么、你需要做什么”，不说“AI 很聪明”。
2. **平实**：少用形容词，多用动词和事实；能给出数量、范围、限制就给出。
3. **主动**：按钮写动作，结果写发生了什么；“保存更改”之后提示“已保存”。
4. **一致**：一个动作全流程用同一个词；按钮、标题、toast、文档使用同一套术语。
5. **可行动**：错误说明原因和下一步；空状态给出可以做什么，不卖萌、不空泛鼓励。

## 2. 禁用与慎用

| 类型 | 不要写 | 改成 |
|---|---|---|
| 拟人化空话 | “让 AI 理解你的需求”“AI 会思考”“AI 帮你搞定” | “读取项目文件并给出修改建议” |
| 夸大形容词 | “智能、全面、轻松、无缝、一键、极速、强大” | 删除，或换成可验证的事实 |
| 不可验证承诺 | “降低 AI 率”“保证通过”“ATS 友好”“查重率 0” | “检查了什么、没检查什么、结果是什么” |
| 伪造社会证明 | 编造用户数、通过率、合作学校、客户 logo | 只写真实可核验的信息 |
| 机械摘要 | 每轮重复“已完成以下步骤” | 只在与上一轮有变化时总结 |
| 重复提醒 | 每段都提醒“请检查 AI 内容” | 在关键节点提示一次，保留 AI 声明 |
| 过度共情 | “别担心”“没关系”“我理解你的感受” | 直接说明问题与下一步 |
| 伪专业黑话 | “赋能、闭环、抓手、心智、范式” | 用用户能懂的具体词 |

## 3. 必须保留的表达

这些不是 AI 口吻，而是产品边界，不能为了“去 AI 化”删掉：

- “AI 草稿”——让用户知道哪些内容是模型生成的。
- “AI 使用声明”——论文/报告导出包中的披露。
- “未验证”“未运行”“不支持”“可能失真”——验证与文档保真报告中的事实。
- “无容器隔离”——本地模式的真实安全边界。
- “不代写整篇论文”“不降重”“不做 AIGC 检测”“不伪造引用”——论文模式的边界。
- “不承诺通过率/录用率”——简历与 ATS 检查的边界。

## 4. 场景写法

### 4.1 宣传页

- 先写用户能完成什么，再写 Nova 怎么做到；不先写“AI 能力”。
- 每句承诺都要能在产品里找到对应入口或文档。
- 未上线能力不写“已有”；可以写“路线图”并链接到路线图。
- 不写“最适合”“第一”“唯一”等无法证明的排名。

### 4.2 论文对话

- 直接说下一步：“先确认选题方向，再列提纲。”
- 一次最多问 1–3 个实质问题；给默认动作和“暂不确定”。
- 不写“我已经为你完成了整篇论文”；写“这是第 2 章草稿，标为 AI 草稿，需要你确认或修改”。
- 引用/数据必须带来源或标“未核实”。

### 4.3 开发 Agent

- 说清执行环境：“在 Docker 沙箱中运行”“在本机运行，无容器隔离”。
- 说清结果：“3 个测试通过，1 个失败，2 个跳过”，不写“测试通过”掩盖失败。
- 说清外部动作：“将创建 draft PR，需要你授权”；不写“已自动发布”。

### 4.4 远程通知

- 只写任务 ID、脱敏标题、状态、下一步；不写源码、路径、密钥、完整日志。
- 示例：“任务 #12 已完成，打开工作台查看结果。”  
  不写：“你的项目 /Users/.../secret 已修好，token 是 ...”。

### 4.5 错误/空状态

- 错误：发生了什么 + 为什么 + 下一步。  
  示例：“PDF 组件未安装。点击下载 LibreOffice 组件，或先导出 DOCX。”
- 空状态：当前没有什么 + 可以做什么。  
  示例：“还没有文档项目。选择一个本地目录开始，或在 `/guide` 查看目录结构。”

## 5. 词表

### 推荐

| 概念 | 用 | 不用 |
|---|---|---|
| 模型生成的内容 | AI 草稿、模型生成 | AI 创作、智能撰写 |
| 执行 | 运行、执行、在沙箱中运行 | 智能执行、自动搞定 |
| 检查 | 检查、核对、验证 | 智能检测、全面体检 |
| 文档 | 文档、项目、草稿 | 作品、成果（除非用户自己的说法） |
| 远程 | 手机工作台、远程连接 | 云控制、微信控制 |
| 简历 | 岗位版本、事实库、JD | 简历优化神器、保过简历 |

### 禁用词（用户可见文案）

```text
让 AI 理解、AI 会思考、AI 帮你搞定
智能、全面、轻松、无缝、一键、极速、强大
降低 AI 率、降 AIGC、保证通过、ATS 友好、查重率 0
赋能、闭环、抓手、心智、范式
```

> 说明：技术文档、内部设计文档可以出现“智能体”“Agent”等术语；本规范约束的是**用户可见文案**。代码标识符、API 字段、日志不受此表约束。

## 6. 检查方式

M1 先提供人工检查清单；M3 加入 CI 自动检查。

### 6.1 人工检查清单

- [ ] 这句话是否在描述一个可验证的行为或事实？
- [ ] 是否出现了禁用词？
- [ ] 是否承诺了产品做不到的结果？
- [ ] 是否隐藏了 AI 参与、失败、未运行或不支持？
- [ ] 是否说明了执行环境（容器/本机）与外部副作用？
- [ ] 按钮、标题、toast、文档是否使用同一个词？
- [ ] 错误是否说明了下一步？
- [ ] 通知是否只含脱敏信息？

### 6.2 自动检查（M3）

计划新增 `scripts/check-copy.mjs`：

1. 扫描 `frontend/src`、`backend/app` 中的用户可见字符串（JSX 文本、提示词、通知模板）。
2. 命中禁用词时失败，并输出文件:行号。
3. 允许 `docs/`、测试、内部注释通过；允许在 `COPY_ALLOWLIST` 中登记确有必要出现的词。
4. CI 与本地 `npm run copy:check` 使用同一份词表。

## 7. 变更流程

1. 新增/修改用户可见文案时，先对照本规范。
2. 如果必须使用禁用词（例如引用用户原话、法律文本），在 PR 中说明理由并加入 allowlist。
3. 每次里程碑结束，复核宣传页、`/guide` 与实际能力是否一致。
4. 删除不再成立的承诺；不把“以后会做”写成“已有”。
