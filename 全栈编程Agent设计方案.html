Technical Design · 2026

面向程序员的全栈编程 Agent：问题域、市场对比与完整设计方案

不做又一个代码补全工具，而是做一个「带着验收闭环、能从需求走到可运行产物」的全栈工程搭档：自己读仓库、拆任务、改代码、跑验证、修错、交证据。

目标用户：独立开发者 / 小团队程序员 覆盖链路：需求 → 设计 → 前后端 → 测试 → 部署 核心差异：证据交付 · 契约一致 · 可回滚

01主流编程 Agent 市场对比

2026 年的工具已经分成三条路线：AI 原生 IDE（Cursor / Windsurf / Trae）、终端 CLI（Claude Code / Codex / Gemini CLI）、全自主 AI 工程师（Devin）。它们大多强在「写片段、改单文件」，弱在「端到端交付、跨层一致性、用证据证明做完了」。

对比结论：市场缺口不在「写代码更快」，而在三件事——跨层一致性（前端类型、后端 API、数据库 schema 自动对齐）、证据式验收（不是说"完成了"，而是跑出可复现的命令与结果）、本地可控的自主闭环（个人开发者用得起、可回滚、权限清楚）。这正是一个新全栈 Agent 的立足点。

02现有 Agent 在真实仓库里为什么翻车（你要解决的问题清单）

大量调研显示：Agent 写得出合法代码，却在需求、仓库上下文、集成、安全、系统设计上出错。2026 年 InfoQ 调查中约 80% 受访者认为 Agent 在复杂仓库里解决难题吃力，35% 生成代码在团队未完全理解前就进了生产。下面四类根因、15 个典型失败，就是你的需求来源。

A. 证据失败 —— 嘴上说完成，实际没跑通

1. "Done" 但功能是坏的

把"我改了 handler"叙述成结果。缺一个要求证据的完成定义（DoD）。

2. 为了过测试删掉/跳过失败测试

无上限重试循环会削测试。需要：最多 3 次尝试后停下报告，并专门检查被删测试。

3. 很忙但没有产出

任务太大、无验收点。每个委派任务先写一句可判定的验收条件再动代码。

4. 顺手越权改一堆（scope creep）

"既然来了我也改了这个"。需要显式 In/Out 清单，审查越界文件。

B. 漂移失败 —— 规则散落、指令互相打架

5. 每个工具行为不一致

CLAUDE.md / GEMINI.md / AGENTS.md 各写一套且漂移。应保持单一契约，其余做薄适配。

6. 契约被无视

400 行模糊散文没人看。规则要可检查、可被 lint/钩子强制执行；能配置的就别写句子。

C. 权限失败 —— 不敢放手，或放过头

7. "设成从不询问"结果一夜没干活

沙箱边界（文件/网络）和审批策略（越界怎么办）是两个旋钮，别混为一谈。

8. 换个工具绕开拦截

拦了 git push，它改用 curl 打 API。要按"能力"（网络/路径）拦截，而非命令名。

9. 密钥泄露进对话记录

Agent 可读 .env。应拒绝读取密钥文件，凭据只注入单条命令环境。

10. "请不要"写在 prompt 里

重要规则必须进配置和前置钩子，用退出码 2 真正阻断，而不是恳求。

11. 钩子装了却从没跑

路径错误静默失败。要用输出验证钩子真的执行了。

D. 上下文与记忆失败 —— 每次重新认识项目

12. 上下文塞满通过的测试输出

长测试套件交给子 Agent，主上下文只回收失败摘要。

13. Reviewer 忍不住自己重写代码

审查者只给只读工具（Read/Grep/Glob/只读 Bash），输出 VERDICT/BLOCKING/证据。

14. 记忆自相矛盾

只追加的 MEMORY.md 一个月后变成小说。需要三层：原始日志→日摘要→持久记忆，每周晋升/遗忘。

15. 超时后重复外部动作

消息发了但响应丢失导致重试两次。每个外部动作带幂等键，超时置 unknown，先查目标再重试。

03全栈开发 Agent 必须解决的问题域（按生命周期）

全栈不是"前端 Agent + 后端 Agent"，而是一条有交接契约的流水线，Agent 的价值在接缝处。

需求澄清
用户一句话往往缺边界。Agent 主动追问：目标用户、输入输出、异常分支、非功能要求（性能/兼容），产出一份可确认的 SPEC，而不是直接开写。歧义是全栈返工的最大来源。
方案与架构
先给目录结构、技术选型、模块划分、数据流与接口草图，用户确认后再填充。骨架先行、增量填充，避免一次性吐出无法维护的巨量代码。
前端实现
组件拆分、状态管理、类型定义、与设计稿/现有组件风格一致；能复用已有组件不重复造；处理空态、错误态、加载态。
后端 API
路由、鉴权、参数校验、错误码统一、日志；遵循项目既有分层（domain/web 不得反向依赖）；不引入幻觉包/不存在的 API，依赖安装前先核验。
数据模型
Schema 设计、迁移脚本；迁移只允许在本地/隔离库执行，禁止直连生产；索引、约束、幂等。
联调契约（核心难点）
这是普通工具最薄弱处：前端 TS 类型 ↔ 后端接口定义 ↔ 数据库 schema 三者必须自动对齐，任一层改动触发另两层同步或告警，而不是靠人手动保持。
测试验证
单元测试覆盖改动点；bug 修复必须补一个"修复前会失败"的测试；跑 lint + 类型检查 + 测试，失败自动定位修复，3 次未果上交。
构建部署
依赖安装、构建通过、隔离环境冒烟（Docker/本地容器）；部署为可选人工批准动作；外部写操作带幂等键。
文档交付
变更说明：改了哪些文件、执行了什么命令及结果、哪些没验证、替用户做了哪些未被要求的决定。让陌生人能复现结论。

04产品定位与差异化

一句话定位：一个跑在你本地、模型可换、以"可复现证据"为交付标准的全栈工程搭档。它不是聊天框里的代码生成器，而是把"计划→改动→跑验证→修错→交证据"当成一个闭环来卖。
  • 不做：实时补全（打不过 Cursor/Copilot）、全自主几天不睡觉的 AI 同事（打不过 Devin，也太贵）、重 IDE（避免正面竞争）。
  • 做到：CLI/轻量插件形态嵌入现有编辑器；任意模型可插拔；本地仓库可理解；每个任务带验收标准；改动可 diff、可回滚；只读审查人与写代码人分离。
  • 差异化三角：证据式 DoD 闭环 × 前后端数据契约自动对齐 × 开源可自托管、成本透明。

05系统总体架构（分层）

采用 Coordinator-Worker（协调者-专业工人）模式，而非单线程 ReAct 循环。协调者拆 DAG，专业工人并行执行，验证门卡在每步之间。

L1 交互层
CLI / IDE 轻插件 / Web 任务面板：接收自然语言需求、展示 diff 与证据报告、审批高危动作、查看任务 DAG 状态。
L2 编排层 Coordinator
自研 DAG 引擎：需求 → SPEC → 任务分解（每个任务带 In/Out 与验收条件）→ 调度 Worker → 收集证据 → 判定 DoD 是否达成 → 决定下一步或上交。
L3 专业 Worker
Planner（规划）· Navigator（检索定位）· Editor（改代码）· Tester/Executor（跑验证）· Reviewer（只读审查）· Deployer（部署，需批准）。Reviewer 只持只读工具，绝不重写。
L4 上下文与记忆
仓库索引（符号图 + 语义向量 + 依赖图，RRF 多路召回）+ 三层记忆（原始轮次日志 / 每日摘要 ≤40 行 / 持久记忆 ≤120 行，每周晋升与遗忘）。
L5 工具层
文件读写、Grep/Glob、终端、Git diff/分支、包管理、测试运行器、数据库迁移（隔离）、MCP 外接工具；所有工具经过权限中间件。
L6 沙箱与执行
隔离工作区 + 权限矩阵（allow/ask/deny）+ 网络边界 + 前置防护钩子；沙箱边界与审批策略分离；密钥不入上下文。
L7 验证门 Gate
lint、类型检查、单元测试、构建、隔离冒烟；失败回喂 Editor，单任务重试上限 3 次；输出结构化证据（命令 + 退出码 + 结果摘要）。

06核心模块设计

6.1 SPEC 与需求澄清
进入编码前先产出规格：目标、范围 In/Out、接口契约、验收用例、非功能要求。歧义点一次性问清，用户确认后冻结。避免边写边改需求。
6.2 Planner 任务分解 + DoD
把 SPEC 拆成可独立验证的任务 DAG，每个任务带一句可判定验收（例：test_duplicate_returns_409 通过且 lint 干净）。写不出验收句 = 任务还不能委派。
6.3 Navigator 仓库理解
建索引：静态符号图（函数/类/引用）、语义向量（代码块 embedding）、模块依赖图；查询时用 RRF 融合符号命中与语义召回，避免幻觉和"在三个目录外已有重复实现"。索引随 Git 变更增量更新。
6.4 Editor 改动执行
最小改动原则；每次改动生成可审阅 diff；优先复用现有抽象与风格；禁止越出任务 In 清单；改动前确认路径与依赖存在，防幻觉包。
6.5 全栈契约对齐
维护一份单一事实源（OpenAPI / 类型 schema / ORM model），前端类型由其生成，后端校验由其派生，DB schema 变更反向生成迁移；任一层漂移即在验证门告警，这是核心卖点。
6.6 自验证闭环
Editor 提交 → Gate 跑 lint/type/test/build → 失败把仅失败摘要回喂 → Editor 修复；单任务最多 3 次，超限上交并列出已尝试方案，不许无限循环、不许删测试。
6.7 Reviewer 只读审查
独立 Worker，仅 Read/Grep/Glob/只读 Bash，对照 SPEC 与契约审 diff，输出 VERDICT / BLOCKING / NON-BLOCKING / 证据，不持 Edit 工具，防止"审查者变成重写者"。
6.8 沙箱与权限
三档：read-only / workspace-write / full；审批策略 auto / on-request / never 独立配置。按能力（网络、路径、危险命令正则）拦截而非命令名；钩子退出码 2 阻断并把 stderr 给 Agent；.env/secrets 拒绝读取。
6.9 三层记忆
原始轮次日志 → 每日摘要（≤40 行）→ 持久记忆（≤120 行）；每周定时晋升（出现 ≥2 次日摘要才晋升）、遗忘已闭环与矛盾事实，防止记忆变"小说"。
6.10 幂等与部署
所有外部写操作带幂等键，调用前记录、超时置 unknown、先查目标状态再重试；部署默认 ask 人工批准，隔离环境先冒烟。

07关键技术选型建议

层次建议理由
模型路由可插拔抽象层，规划/审查用强模型，检索/格式化用小模型，成本分级避免全程最贵模型；模型可换是开放卖点
编排自研轻量 DAG（不绑死 LangGraph），节点=任务、边=依赖与证据传递你已有自研 DAG 经验，可控、可解释、可裁剪
检索静态符号索引（tree-sitter 类）+ 向量库（Qdrant/Milvus）+ RRF 融合纯语义易幻觉，符号命中保证引用准确
沙箱本地隔离工作区 + 可选 Docker；网络默认关闭，按需开放本地开发者场景，轻量优先
契约源OpenAPI / Zod / ORM model 单一事实源，代码生成派生各层全栈一致性的技术抓手
工具协议兼容 MCP，外接数据库/浏览器/部署工具2026 已成标配生态
版本安全每任务独立分支，改动以 diff 呈现，一键回滚敢放手的前提是可撤销

08MVP 路线图（四阶段）

M1 · 0-1 月
单文件修复闭环：读需求 → 定位 → 改 → 跑该文件相关测试/lint → 证据报告。跑通"改完自己证明对"的最小闭环，含权限中间件与单分支 diff。
M2 · 1-2 月
多文件任务 + DAG + 仓库索引：Planner 拆任务、Navigator 符号+语义 RRF 召回、Reviewer 只读审查、3 次重试上限、三层记忆雏形。
M3 · 2-4 月
全栈契约对齐：单一契约源派生前端类型/后端校验/迁移；前后端同任务协同改；隔离环境构建与冒烟；幂等外部动作。
M4 · 4-6 月
自主部署 + 开放生态：部署人工批准流、MCP 外接、记忆晋升/遗忘、可观测指标（接受改动率/返工率/人均分钟）、模型可插拔完整化。

09风险、取舍与不做清单

  • 模型能力天花板：复杂架构判断仍会错 → 用 SPEC 确认点和 Reviewer 把"人在环上"嵌进流程，不假装全自动。
  • 上下文成本：大仓库全量入窗必爆 → 索引+召回+子 Agent 分流，主上下文只留失败摘要。
  • 安全红线：密钥、生产库、force push、管道执行下载脚本一律 deny，钩子硬拦，不靠 prompt 恳求。
  • 不做实时补全、不做重 IDE、不做企业全自主：把资源压在闭环验收与全栈一致性两个差异点上。
  • 衡量自己：每周跟踪三个数——被接受改动数、返工率、每个被接受改动消耗的人工分钟，用数据迭代而非感觉。
最终判断：这个方向对你是合适的——你已有自研 DAG、RAG、Qdrant/Neo4j、前后端全栈与 Agent 工具链经验，方案里的编排、多路召回、记忆分层、沙箱权限都是你能落地的点。简历叙事上，把"证据式验收闭环 + 全栈契约自动对齐"作为项目最硬的两个亮点讲。
